Part I - The Project README (verbatim)

Reproduced exactly as it appears in the repository.

Video Intake & Blender VSE Pipeline

Automates the journey from raw multi-camera footage (iPhone, GoPro, OBS, Canon Vixia / 7D, iVue Rincon, stills) to an edit-ready Blender VSE project. Run the four scripts in order, then do your manual editing in Blender, then use the two marker scripts to prep for and clean up after the Keyboard Maestro cutting macro.

Pipeline Overview

Raw footage (iPhone · GoPro · OBS · Canon · iVue · stills)
        │
        ▼
1. ingest.py          — scan folder, extract metadata; optionally pair clips
                        with external audio or sync two camera angles;
                        write manifest
        │
        ▼
2. transcode.py       — normalize all media to SDR · CFR 29.97 · 16:9 MP4;
                        conform paired audio + measure offsets (external
                        audio and camera-pairs)
        │
        ▼
3. import-vse.py      — create Blender project, import clips chronologically;
                        overlap synced camera pairs on separate tracks
        │
        ▼
   [ manual editing in Blender — place F / u markers ]
        │
        ▼
4. vse-validate-markers.py   — validate marker pairs, save _cut.blend,
                               print KM loop count
        │
        ▼
   [ run Keyboard Maestro cutting macro —
     blender-km-macros/scripts/trigger.sh N ]
        │
        ▼
5. vse-remove-markers.py     — wipe all timeline markers, save in place
        │
        ▼
   Edit-ready Blender project

Scripts

1 — ingest.py

Scans a footage folder recursively, extracts metadata via ffprobe / exiftool, and writes three output files to <input_dir>/_ingest/:

  • manifest.json — machine-readable, consumed by transcode.py
  • clips_ordered.txt — human-readable chronological list
  • ingest_report.md — counts, flags (HDR / VFR / vertical / missing timestamps / naive-local timestamps normalized to UTC), external-audio + camera-sync pairings, timeline gaps

What it detects per file: source, camera model, media type, orientation, dimensions, duration, FPS, HDR, VFR, creation timestamp.

Camera identification. source is a short token used downstream: iphone, gopro, obs, or a vendor brand (canon, sony, panasonic, …) for anything else. iPhones and GoPros come from cheap ffprobe/filename heuristics; OBS screen captures are identified by their default filename pattern (YYYY-MM-DD HH-MM-SS.mkv); everything else falls through to an exiftool Make/Model lookup, so new camera brands work without code changes. camera_model carries the full string exposed by the file — e.g. iPhone 16 Pro, HERO12 Black, Canon EOS 7D, Canon VIXIA HF R40. Two iPhones of different generations in the same shoot show up distinctly in this field. OBS captures and anything else with no Make/Model leave it as — in the report.

External audio pairing. After scanning, ingest.py asks whether any video clips have a separate, higher-quality audio file (iPhone Voice Memo, dedicated recorder, etc.). If yes, you drag-and-drop each video clip and its matching audio file. The pairing is written to manifest.json as an external_audio field — no heavy processing happens at ingest time. The video clip keeps its native audio; in transcode.py (step 2) the paired file is conformed to a sibling WAV, audio-offset-finder measures the offset, and in import-vse.py (step 3) the conformed audio is dropped onto a separate VSE track aligned with the video.

Camera-sync pairing. ingest.py then asks whether any two clips captured the same take from different cameras — e.g. an OBS screen recording (with a good USB mic) plus a Canon 7D angle. You drag-and-drop the base clip (its audio anchors the sync, typically OBS) and the second camera clip. Both must be scanned project files, and — unlike external audio — both videos are preserved as separate files. The pairing is written to manifest.json as a shared sync_group id with sync_base on the base clip. The actual offset measurement happens in transcode.py (step 2), and import-vse.py (step 3) overlaps the pair on separate Blender tracks.

Timezone normalization. iPhone and GoPro write creation_time in true UTC. Other cameras — Canon Vixia, Canon 7D, iVue Rincon — write naive local wall-clock time but still label it Z, so left alone they sort hours away from the Apple/GoPro clips. OBS writes no creation_time tag at all, but its default filename template (%CCYY-%MM-%DD %hh-%mm-%ss.mkv) encodes the local start-of-recording time, which ingest parses as another naive-local source. Ingest then reads the real local offset from an iPhone/GoPro clip in the same batch (e.g. -0400) and rewrites all naive clips to true UTC so every clip shares one clock. If there is no Apple/GoPro clip in the batch it falls back to this machine's timezone (and warns) — use --local-offset to set it explicitly. Any per-camera embedded timezone tag is deliberately ignored, since it is often misconfigured (the Vixia reports -05:00 even when shooting in -04:00). Displayed times in the reports are local wall-clock.

python3 ingest.py /path/to/footage
python3 ingest.py /path/to/footage --output /path/to/output_dir
python3 ingest.py /path/to/footage --local-offset -04:00   # footage shot in a zone with no Apple/GoPro clip
python3 ingest.py          # prompted — supports drag-and-drop

Flags / options:

FlagDescription
--output, -oCustom output directory (default: <input_dir>/_ingest)
--local-offsetUTC offset of the footage's local time, e.g. -04:00. Overrides offset detection for naive-local cameras (Canon, iVue). Default: read from an iPhone/GoPro clip, else this machine's timezone.

2 — transcode.py

Reads _ingest/manifest.json and normalizes every file. All output lands in _ingest/transcoded/. Already-transcoded files are skipped, so re-runs are safe.

What it does per file type:

InputTransform
Still image6-second slow-zoom MP4: 1s static lead-in + 5s Ken Burns zoom (libx264 · 29.97 fps · 1920×1080)
iPhone HDR videoavconvert PresetAppleM4V1080pHD → SDR .m4v, then ffmpeg for VFR/vertical/remux
Other HDR videoffmpeg zscale tone-map → SDR
VFR video, or fps ≠ project rate (e.g. OBS at 30.000)ffmpeg -fps_mode cfr → CFR 29.97 — avoids Blender VSE auto-flipping the scene fps and the 0.1% playback drift that puts video out of sync with audio
Vertical videoffmpeg blurred 16:9 letterbox (portrait centred on blurred+darkened background)
GoPro / clean videostream-copy (fast, no re-encode)

Audio is normalized to -16 LUFS / -1.5 dBTP via loudnorm on all re-encoded clips.

External audio overlay. Clips that have an external_audio entry in the manifest (set during ingest) are transcoded normally — the video keeps its native audio. Afterward, the paired audio file is conformed to a sibling WAV next to the transcoded MP4 (<basename>_extaudio.wav) at the video's sample rate and channel count; PCM WAV avoids the AAC priming delay and on-the-fly resampling that drift Voice Memo (.m4a) tracks during VSE playback. audio-offset-finder then measures the offset between the conformed WAV and the transcoded video, and writes external_audio_conformed_path + external_audio_offset_s onto the entry. import-vse.py (step 3) reads those and adds the WAV as a sound strip on a separate track, time-aligned with the video.

Camera-sync offsets. For clips tagged with a sync_group (set during ingest), both angles are transcoded normally as separate files — nothing is muxed. Afterward, audio-offset-finder measures the audio offset between the two transcoded clips and writes sync_offset_s onto the second-camera entry. If the measurement fails or scores low, the pair is left at offset 0 with a warning (nudge it in Blender). import-vse.py uses this offset to align the pair on separate tracks.

On completion writes _ingest/transcoded/manifest_transcoded.json — the input for import-vse.py.

python3 transcode.py /path/to/project_folder
python3 transcode.py /path/to/project_folder --dry-run
python3 transcode.py          # prompted — supports drag-and-drop

Flags / options:

FlagDescription
--output, -oCustom output directory
--fpsTarget CFR frame rate (default: 29.97)
--dry-runPrint what would run, write nothing
--no-loudnormSkip audio loudness normalization

3 — import-vse.py

Reads manifest_transcoded.json, prompts for project name and resolution, then launches Blender headlessly to create a .blend file with all clips placed on the VSE timeline in chronological order. Applies the Video Editing workspace layout and writes blender_import.log.

Per-camera channel routing. Every strip from the same physical camera lands on a shared VSE channel so per-camera mute/solo is one click. The routing key is the entry's camera_model (e.g. Canon EOS 7D, Canon VIXIA HF R40, iPhone 16 Pro, HERO12 Black), falling back to source for clips with no exposed model (OBS, anything without EXIF Make/Model) — so a Canon 7D and a Canon VIXIA never collide on one lane even though both report source: "canon". Cameras fill channel pairs from ch1 upward in first-seen chronological order; whichever camera shoots first claims ch1/2. OBS is special-cased to always pin to ch1/2 (the bottom row) if any OBS clip is present, regardless of batch order, so the screen capture sits below the paired camera in a sync pair. External-audio sources (zoom, voice-memo, or a file-extension bucket — set by ingest.py from filename pattern + ffprobe handler tag) fill single channels above the highest camera pair. Channels are stable within a project: a second clip from the same camera lands on the same lane as the first, even if other cameras appear in between.

Synced camera pairs. A sync_group pair is placed as a single chronological slot with the two angles overlapping on separate tracks: each clip goes to its own camera's lane (e.g. an OBS+7D pair lands OBS on the OBS lane and 7D on the Canon lane, never colliding because they're different sources). The angle is shifted by the measured sync_offset_s so the same moment lines up. Both audio strips are imported active (mix or mute them in Blender). The pair reserves its combined span, after which solo clips resume sequentially.

External-audio overlays. A clip with external_audio_conformed_path is placed similarly: the video sits on its camera's lane (with its native audio intact), and the conformed audio WAV sits as a sound strip on its audio-source-assigned channel (e.g. every Zoom H1 file on one ch, every Voice Memo on another), shifted by external_audio_offset_s. Whichever started first anchors the slot at the cursor position — if the camera recorded before the audio, the previous clip butts up to the camera start; if the audio recorded before the video, the previous clip butts up to the audio start. The slot's end is whichever strip ends later.

python3 import-vse.py /path/to/project_folder
python3 import-vse.py /path/to/project_folder --name my_project
python3 import-vse.py          # prompted — supports drag-and-drop

Flags / options:

FlagDescription
--name, -nProject and .blend filename
--blenderPath to Blender executable (auto-detected if omitted)
--dry-runShow import order and Blender command without running

Prompted interactively: project name, resolution (1080p or 4K), confirmation of clip order.

4 — vse-validate-markers.py

Opens a .blend file in Blender headlessly, reads all timeline markers, and validates them as F / u pairs before you run the Keyboard Maestro cutting macro.

Marker convention: markers must come in pairs — the start of a keep-range is named F1, F2, etc.; the matching end is named exactly u. Each pair defines one segment to retain.

What it checks:

  • Even number of markers (every start has an end)
  • Alternating F… / u naming
  • No overlapping ranges

On success: saves a _cut.blend copy of your project and prints the number of KM macro loops needed.

python3 vse-validate-markers.py /path/to/project.blend
python3 vse-validate-markers.py          # prompted — supports drag-and-drop

4.5 — Keyboard Maestro cutting macro (blender-km-macros/)

Between validating markers and removing them, run the Keyboard Maestro macro that performs the actual cuts in Blender. It lives in blender-km-macros/, which has the full setup guide — importing the .kmmacros files into Keyboard Maestro and the safety / TEST flow.

Once the macros are imported, trigger the cutting macro with the loop count that step 4 printed:

./blender-km-macros/scripts/trigger.sh <N>          # N = KM loop count from step 4
./blender-km-macros/scripts/trigger.sh --test <N>   # dry run — deletes nothing

trigger.sh won't fire if Blender isn't running. See the subfolder README for the macro internals and import notes.

5 — vse-remove-markers.py

Opens a .blend file in Blender headlessly, removes every timeline marker, and saves in place. Run this after the Keyboard Maestro macro has finished cutting.

python3 vse-remove-markers.py /path/to/project.blend
python3 vse-remove-markers.py          # prompted — supports drag-and-drop

Typical Full Run

# 1. Ingest
python3 ingest.py ~/footage/trip

# 2. Transcode (can take a while — grab a coffee)
python3 transcode.py ~/footage/trip

# 3. Import into Blender
python3 import-vse.py ~/footage/trip --name trip_edit

# --- Open trip_edit.blend, do manual editing, place F/u markers ---

# 4. Validate markers
python3 vse-validate-markers.py ~/footage/trip/trip_edit.blend

# 4.5 Run the Keyboard Maestro cutting macro (N = loop count printed by step 4)
./blender-km-macros/scripts/trigger.sh <N>

# 5. Clean up markers
python3 vse-remove-markers.py ~/footage/trip/trip_edit_cut.blend

Each script also prints the exact command to run for the next stage when it finishes, threaded with the paths it just produced — so in practice you can also just copy-paste from one script's terminal output into the next.

Platform Notes

  • macOS is the primary target. avconvert (iPhone HDR→SDR) is macOS-only; on Linux, the pipeline falls back to ffmpeg's zscale tone-map automatically.
  • All scripts support drag-and-drop path input when run without arguments — useful in Terminal on macOS.
  • Blender is auto-detected on PATH and at common install locations (/Applications/Blender.app on macOS, /usr/bin/blender / /usr/local/bin/blender / ~/blender/blender on Linux). Pass --blender /path/to/blender to override.

Roadmap

  • Enumerate .blend outputs on each cut run — vse-validate-markers.py currently writes <name>_cut.blend, overwriting any previous cut from earlier runs of the same project. Suffix subsequent runs with _2, _3, etc. so historical cuts are preserved. Companion change: import-vse.py should suggest <name>_1.blend as the default on creation so the numbering convention is consistent from the project's first .blend onward.
  • Proxy generation — re-add redo_proxies.py as a post-import step; build 25% proxies for smooth VSE playback without leaving Blender.
  • Subtitles for the Blender timeline itself — the captions/ add-on already covers post-export caption generation (Whisper → SRT → soft-embedded mov_text or hard-burn). What's still on the wishlist: importing SRT / VTT as text strips directly onto the Blender VSE timeline (so captions are visible during editing rather than only on the final render), and a multi-language pass that produces several mov_text streams in one mux. Auto-translation is out of scope.
  • After Effects export — convert the VSE timeline to an AE-compatible project file (via ExtendScript or aescript bridge) for finishing in After Effects.

Part II - What It Is & Why It Exists

You shoot an event on whatever is in your hands: an iPhone, a GoPro, an older Canon Vixia camcorder, a Canon 7D, a little iVue Rincon action cam, an OBS screen recording of something running on the laptop, plus a handful of still photos. You end up with a folder full of clips that disagree with each other on almost everything that matters to an editor:

  • They disagree on time. iPhone and GoPro stamp every clip in true UTC. The Canons and the iVue write local wall-clock time but mislabel it as Z (UTC). OBS writes no time at all in the file — only in the filename. Sorted naively, the camcorder clips land hours away from the phone clips and OBS clips fall to the very end, so your timeline is shuffled out of real order.
  • They disagree on color. iPhone video is HDR (high dynamic range). Dropped onto an SDR timeline next to GoPro footage it looks washed-out or wrong.
  • They disagree on frame timing. Phones often record VFR (variable frame rate) to save space; OBS records at exactly 30.000 fps (not 29.97); an editor wants CFR at one matching rate or playback drifts and audio slips against the rest of the project.
  • They disagree on shape. A vertical phone clip on a 16:9 timeline leaves ugly black bars, or gets stretched.
  • They disagree on being video at all. Stills are not clips; they have no duration and cannot sit on a video track as-is.
  • They disagree on audio quality. A clip shot with a camera's built-in mic may have poor audio when a dedicated recorder (Zoom H1) or an iPhone Voice Memo was running nearby — those two tracks need to be synced and dropped onto a separate row of the timeline next to the original.
  • They sometimes captured the same moment. A screen recording (OBS) and a DSLR pointed at you both running during one take are not two consecutive clips — they are two angles of one moment that need to overlap on the timeline, perfectly time-aligned, so you can cut between them.

The Video Intake Pipeline exists to erase every one of those disagreements before you start editing. You point it at the messy folder; it hands back a single Blender Video Sequence Editor (VSE) project where every clip is the same flavor — SDR, constant 29.97 fps, 16:9, normalized audio — laid in true chronological order, with each camera routed to its own VSE channel and each paired audio recorder on its own channel above. The goal is simple: spend your energy editing, not wrangling formats.

Part III - How It Is Structured

The pipeline is not one big program. It is five small command-line tools that hand work to each other through plain files on disk. Think of it as an assembly line where the conveyor belt is a JSON file.

ingest.py      -->  manifest.json (+ clips_ordered.txt, ingest_report.md)
transcode.py   -->  manifest_transcoded.json  (+ normalized .mp4 clips,
                                                 + sibling _extaudio.wav
                                                   for any external-audio pair)
import-vse.py  -->  project.blend  (+ blender_import.log with channel routing)
               [ you edit in Blender, place F/u markers ]
vse-validate-markers.py  -->  project_cut.blend  (+ a "loop count")
               [ Keyboard Maestro macro does the cutting ]
vse-remove-markers.py    -->  clean project_cut.blend

Everything a downstream tool needs is written by the upstream tool into the _ingest/ folder. The manifest is the contract between stages: ingest describes every file (where it is, when it was shot, whether it is HDR/VFR/vertical, whether it has an external audio file to sync); transcode reads that description, normalizes the media, and rewrites the manifest with the new file paths and corrected flags; import reads the final manifest and never has to re-sort anything because the order is already baked in.

Patterns shared by every script

Once you have read one of these scripts, you have half-read the others. They share a small set of idioms on purpose:

  • Drag-and-drop friendly. Run any script with no argument and it prompts you to drag a folder (or .blend) into the Terminal. A sanitize_path() helper strips the quotes and backslash-escapes that macOS adds when you drop a path.
  • Tool auto-discovery. Each script hunts for ffmpeg, blender, and friends on your PATH first, then at well-known macOS/Linux locations, and only then gives up with an install hint. This is what makes the same code run on a Mac and on Linux Mint.
  • Headless Blender by code generation. The three Blender scripts never open a window. They write a small Python program into a temporary file, launch blender --background --python that_file.py, and watch Blender's output for a sentinel line (IMPORT_COMPLETE, VALIDATION_COMPLETE, REMOVE_COMPLETE). Seeing the sentinel is how the wrapper knows the job truly finished, not just that Blender exited.
  • Idempotent re-runs. Transcode skips any clip whose output already exists, so re-running after a crash resumes instead of redoing everything. Ingest prunes its own output folder from the scan so it never re-ingests its own transcoded copies.
  • Colored, streaming output. Helpers like ok(), warn(), skip() print green / yellow / purple status as work happens, and Blender's own log lines are echoed live with a blender | prefix so a long import never looks frozen.
  • Next-step hints on success. Every script ends by printing the exact command for the next stage, threaded with the paths it just produced — so going from vse-validate-markers.py to the Keyboard Maestro trigger.sh call, or from import-vse.py straight into the open <blend> + validate command, is a copy-paste rather than a recall exercise.

Part IV - How Each Stage Works

Stage 1 -- ingest.py: build the map

Ingest walks the footage folder, inspects every video and image, and writes the manifest plus two human-readable reports. The interesting work is in how it figures things out without trusting any single piece of metadata.

Source detection. It guesses the camera with a cascade: GoPro filename prefixes (GH, GP, GOPR, GL); then ffprobe tags (Apple make → iPhone, GoPro encoder/handler → GoPro); then iPhone naming patterns (IMG_1234, screen recordings); then OBS's default filename template (YYYY-MM-DD HH-MM-SS.mkv) → obs; finally, an exiftool Make/Model lookup turns the manufacturer into a short token like canon, sony, panasonic. Anything still unrecognized is unknown — it still flows through, it just is not special-cased.

Full camera model. Alongside source, ingest records a camera_model field — the full device string the file exposes (iPhone 16 Pro, HERO12 Black, Canon EOS 7D, Canon VIXIA HF R40). iPhones expose the model in ffprobe directly, so it's free; everything else uses an exiftool call. This is what downstream stages key off when routing clips to their own VSE channel — a Canon 7D and a Canon VIXIA both report source: "canon", but their camera_model strings are distinct, so they never collide on one lane.

The timezone fix (the clever part). This is the pipeline's signature trick. A clip only counts as "really UTC" if it carries proof: an Apple make tag or Apple creationdate, or a GoPro signature. iPhone and GoPro pass; the Canon Vixia, Canon 7D, and iVue Rincon do not — they record local time mislabeled as UTC. OBS writes no creation_time tag at all, but its default filename is literally local wall-clock at start of recording (2026-05-30 10-39-21.mkv), so ingest parses that as the timestamp and treats OBS as another naive-local source. Then it:

  1. Collects the true UTC offset from any iPhone/GoPro clip in the batch (it reads the offset baked into Apple's creationdate, e.g. -0400, and takes the most common one).
  2. Rewrites every naive-local clip (Vixia, 7D, iVue, OBS) from that one batch offset into true UTC, so the whole shoot finally shares a single clock.
  3. If there is no iPhone/GoPro clip to learn the offset from, it falls back to this machine's timezone and prints a warning telling you to re-run with --local-offset if the footage was shot elsewhere.

Crucially it ignores any timezone tag the camera itself embedded, because those are routinely wrong (the Vixia happily reports -05:00 while shooting in -04:00, which would re-break the order). Trust the phones; correct the rest.

External audio pairing. After the scan completes, ingest asks whether any video clips have a separate higher-quality audio file — an iPhone Voice Memo, a dedicated recorder, anything with better audio than the camera's built-in mic. If you say yes, it walks you through drag-and-dropping each video clip and its matching audio file one pair at a time. The pairing is written into manifest.json as an external_audio field on the relevant clip entry. Ingest also classifies the recorder so downstream stages know which channel to route it to: filenames matching ZOOM\d → "zoom"; an m4a file with Core Media Audio in its ffprobe handler tag (the iOS encoder signature) → "voice-memo"; otherwise the file extension as a generic bucket. The classification goes onto the manifest as external_audio_source. No heavy processing happens at this point; transcode.py does the sync in step 2.

Camera-sync pairing. After audio pairing, ingest asks whether any two clips captured the same take from different cameras — typically an OBS screen recording plus a DSLR pointed at you. You drag-and-drop the base clip (its audio anchors the sync) and the second-camera clip. Both must be project files already scanned, and — unlike external audio — both videos are preserved as separate files. The pair gets a shared sync_group id on the manifest, plus sync_base: true on the base. Transcode.py measures the offset in step 2; import-vse.py overlaps them on separate VSE tracks in step 3.

Other detectives. Rotation is read from the modern iPhone location — the Display Matrix in the stream's side_data_list, not the legacy rotate tag — and width/height are swapped when a clip is 90/270 degrees so orientation is logical, not pixel-literal. HDR is detected from the color transfer curve (smpte2084 for PQ, arib-std-b67 / hlg for HLG). VFR is inferred when a clip's average and "real" frame rates disagree by more than half a frame. Stills with no usable ffprobe data fall back to ImageMagick identify for size and exiftool for EXIF orientation and timestamp.

What you get. manifest.json (the machine contract), clips_ordered.txt (a quick chronological table), and ingest_report.md — a narrative with per-camera counts, total duration, flagged clips (HDR/VFR/vertical/no-timestamp/normalized-to-UTC), a Pairings section listing every external-audio and camera-sync pair you set up, and any timeline gap longer than 10 minutes, which is a handy way to see where one scene ended and the next began.

Stage 2 -- transcode.py: make everything agree

Transcode reads the manifest and converts each file according to what it is. The whole point is that every output is the same: SDR, CFR 29.97, 16:9, libx264 MP4 with audio normalized to -16 LUFS / -1.5 dBTP.

  • Stills become 6-second clips. A three-pass recipe: ImageMagick pads the photo onto a 4K black canvas; ffmpeg makes a 1-second static lead-in; ffmpeg makes a 5-second slow "Ken Burns" zoom (zoompan, easing from 1.0 to 1.1x); the two are concatenated. The result drops onto the timeline like any clip.
  • iPhone HDR uses Apple's own converter. macOS avconvert with the PresetAppleM4V1080pHD preset does the HDR-to-SDR tone-map (Apple knows its own color science best), then ffmpeg handles any leftover VFR-to-CFR or vertical-to-16:9 work. iPhone clips are always forced to CFR 29.97.
  • Non-Apple HDR uses an ffmpeg tone-map — a zscale -> tonemap=hable -> zscale chain that linearizes, maps highlights with the Hable curve, and lands back in bt709 SDR. (On Linux, where there is no avconvert, all HDR takes this path.)
  • Vertical clips get a blurred 16:9 letterbox. The clip is split into two copies; one is scaled up to fill 1920x1080, heavily Gaussian-blurred (gblur=sigma=120) and darkened to make a soft background; the original portrait is centered on top. Far nicer than black bars.
  • Off-rate clips are forced to CFR 29.97. The big offender is OBS at 30.000 fps (not 29.97). Left alone, Blender's VSE would flip the scene fps when the OBS clip was added — and then back when the next 29.97 clip arrived — and OBS would play at a 0.1% slowdown that puts its video out of sync with any paired audio over the length of the clip. The fix is to re-encode any clip whose native fps differs from the project target (0.01 tolerance covers 30000/1001 jitter) through ffmpeg with -r 30000/1001 -fps_mode cfr. Same path that handles VFR phones.
  • Clean clips at the target rate are stream-copied — GoPro at 29.97, 7D at 29.97, Vixia at 29.97 all pass through untouched, fast and lossless.

Re-encoded video uses CRF 18 (visually lossless) at the fast preset. After each file, transcode re-probes the output to record its true dimensions and clear the HDR/VFR flags. Because it skips any output that already exists, the step is safe to re-run.

External audio overlay. When a manifest entry has an external_audio field, the video is transcoded normally — its native audio is kept. After all the videos are done, a second pass conforms the paired audio file to a sibling WAV next to the transcoded MP4 (<basename>_extaudio.wav), resampled and remixed to match the video's sample rate and channel count. PCM WAV is the on-disk format on purpose: AAC m4a (which Voice Memos write) carries encoder-delay priming samples that Blender's audio loader doesn't compensate for, and Blender's on-the-fly resampling between 44.1 kHz and 48 kHz can accumulate drift over a long clip — both make the synced audio gradually slip against the video. WAV at the video's native rate has no priming offset and no playback-time resampling, so the offset audio-offset-finder measures is the offset Blender will actually play. The measured offset and the WAV path are written onto the manifest entry as external_audio_offset_s and external_audio_conformed_path; import-vse.py uses them in step 3 to drop the WAV onto its own VSE row.

Camera-sync offsets. When two clips share a sync_group, both are transcoded normally as separate files — nothing is muxed. Then audio-offset-finder compares the two transcoded clips' audio to find how far the second-camera clip lags or leads the base, and writes the result as sync_offset_s on the second-camera entry. A confidence score is printed; a score below 10 triggers a warning. If the measurement fails entirely the pair is left at offset 0 with a warning, so you can nudge it manually in Blender. Import-vse.py reads the offset and overlaps the pair on separate tracks in step 3.

On completion transcode writes manifest_transcoded.json — the input for import-vse.py.

Stage 3 -- import-vse.py: build the Blender project

This stage turns the normalized clips into an actual .blend. It detects the frame rate from the first clip, asks you for a project name and resolution (1080p or 4K), shows you the import order for confirmation — including the channel each clip will land on — then generates a Blender Python script and runs it headlessly.

Per-camera channel routing. Before any strip is placed, a pre-scan walks the manifest in chronological order and assigns every unique camera a VSE channel pair, every unique audio recorder a single channel. The routing key is camera_model when present (so iPhone 16 Pro and iPhone 14 get different lanes, and Canon EOS 7D never collides with Canon VIXIA HF R40 even though both share source: "canon"), falling back to source for clips with no exposed model. Lanes fill from ch1 upward — whichever camera shoots first claims ch1/2 — with one exception: OBS is pre-seeded so it always lands on ch1/2 regardless of when its first clip appears, which means in a sync pair the screen capture sits visually below the paired camera every time. External-audio sources (zoom, voice-memo, file-extension buckets) get single channels stacked above the highest camera pair. The result is that muting "all iPhone footage" or "all Zoom audio" in Blender is a single click on the channel header.

Inside the generated Blender script, each item is placed at the current playhead and the playhead advances by the slot's length. Three kinds of slots:

  • Solo clip — a normal movie_strip_add on the clip's camera lane.
  • Sync pair (a sync_group) — both clips placed at the same chronological slot, each on its own camera lane, with the second-camera clip shifted by sync_offset_s so the matching moment lines up. Whichever started recording first anchors the slot at the playhead; the other sits to the right of it. The playhead advances to whichever ends last.
  • External-audio overlay — the video goes on its camera lane (keeping its native audio); the conformed WAV goes on the audio recorder's single channel, shifted by external_audio_offset_s. Same anchor-by-earlier / advance-to-later rule as a sync pair.

After every clip is placed, the script sets scene.frame_end to the last frame of the last strip (so the playable range matches the imported content instead of Blender's default 250), runs view_all on the sequencer so the whole timeline is zoom-fit when you open the file, then loads Blender's built-in Video Editing workspace and saves. A blender_import.log records the channel routing legend and exactly what landed where. The script ends by printing the next-step command — opening the .blend and running vse-validate-markers.py against it.

Stage 4 -- vse-validate-markers.py: check your cut plan

After you edit in Blender, you mark the ranges to keep with timeline markers following one convention: the start of a keep-range is named F1, F2, … and its end is named exactly u. Each F.. -> u pair is one segment to retain.

Validation opens the file headlessly, sorts the markers by frame, and checks: the count is even (every start has an end), the names alternate F.. then u, and no two keep-ranges overlap (a pairwise comparison). If anything is wrong it lists every problem and exits without touching your file. If everything is clean it saves a _cut.blend copy and prints the loop count for the Keyboard Maestro macro — which is pairs - 1, the number of unwanted gaps between your kept segments that the macro will delete. The wrapper script captures both the loop count and the _cut.blend path from Blender's output, so the next-step hint at the end of the run is the fully-resolved trigger.sh <N> command plus the vse-remove-markers.py command that follows — both copy-paste ready.

Stage 4.5 -- the Keyboard Maestro macro: do the cutting

Blender has no clean headless "ripple delete between markers" operation, so the actual cutting is done by simulating the keystrokes a human would press — and that is what Keyboard Maestro automates. The macro lives in blender-km-macros/ and is fired by trigger.sh:

./blender-km-macros/scripts/trigger.sh <N>          # N = loop count from Stage 4
./blender-km-macros/scripts/trigger.sh --test <N>   # rehearse, delete nothing

trigger.sh first checks Blender is actually running (pgrep), then uses osascript to tell the Keyboard Maestro Engine to run the macro, passing N as a parameter. Inside the macro that value arrives as %TriggerValue%, gets stored in a variable BlenderDeleteCount, and drives a Repeat-N-times block of the fixed delete keystrokes. There is a (TEST) twin that runs the same flow but pops a confirmation dialog instead of deleting, so you can rehearse safely.

Stage 5 -- vse-remove-markers.py: tidy up

Once the macro has done its cutting, the F../u markers are just clutter. This last script opens the .blend file, removes every timeline marker, and saves in place — leaving a clean, edit-ready project.

Optional add-on — captions/

After you've rendered your cut Blender project to MP4, the captions/ subfolder offers an opt-in tool (python3 captions/captions.py <file.mp4>) that transcribes the audio with whisper.cpp and either soft-embeds the captions as a toggleable mov_text track in a sibling _subbed.mp4 (default) or hard-burns them into pixels with --burn. The script is stdlib-only Python — it shells out to whisper-cli (Homebrew formula whisper-cpp, Metal-accelerated on Apple Silicon) and ffmpeg, the same architecture as every other pipeline script. No pip install, no venv, no PyTorch — just brew install whisper-cpp and a one-time curl for the model file, both documented in captions/README.md. Many pipeline runs just upload to YouTube and let YouTube do the captioning, and never touch this folder.

Part V - How It Was Made: Design Decisions

A few choices are worth understanding, because they explain why the code looks the way it does.

  • The manifest is a contract, and you can edit it. Because stages talk through manifest.json, you can open it and delete a clip, fix a timestamp, or reorder by hand, and the rest of the pipeline obeys. The format is the API.

  • Generated Blender scripts plus a sentinel string. Rather than fight Blender's Python console, each Blender stage writes a one-shot script to a temp file and watches stdout for a unique "I finished" line. It is a simple, robust way to drive a giant GUI app from a tiny CLI wrapper, and the same trick appears three times.

  • Trust phones, correct camcorders. The timezone normalization deliberately distrusts camera-embedded timezone tags and instead anchors the whole batch to an iPhone/GoPro clock. The most recent relevant commit in the repo is: "ingest: normalize naive-local camera timestamps to UTC."

  • Ingest records intent, transcode does work. The external audio pairing and the camera-sync pairing are both deliberate splits: ingest is fast (metadata only), so asking about pairings there costs nothing. The heavy lifting — running audio-offset-finder, conforming audio to WAV, re-encoding video with ffmpeg — belongs in transcode, which already owns the slow per-file processing loop. The manifest fields (external_audio, sync_group) are the handoff.

  • Overlay, not replace, for external audio. Early versions of the pipeline muxed the paired audio into the video clip, replacing its native audio track. The current version keeps the native audio on the clip and drops the paired file onto its own VSE row — same shape as a sync pair, just with a sound strip instead of a second movie strip. This makes mute/solo decisions an editing choice rather than a baked-in one, and it means the paired audio gets the same per-source channel routing as everything else (every Zoom take on one row, every Voice Memo on another).

  • Conform to PCM WAV before any Blender sees it. AAC m4a (what Voice Memos writes) carries encoder-delay priming samples that Blender's audio loader doesn't compensate for, and Blender's on-the-fly resampling between 44.1 kHz and 48 kHz can slowly drift. Conforming the paired audio to WAV at the video's native sample rate, up front in transcode, eliminates both — the offset audio-offset-finder measures is the offset Blender actually plays back. It's the kind of bug that looks like "Voice Memos always slips" until you understand the format details.

  • Per-camera channel routing keyed on the model, not the brand. The natural editor-friendly grouping is "all iPhone footage on one row, all GoPro on another," so mute/solo is a single click. The first version of this routed on source (brand-only), which collapsed Canon EOS 7D and Canon VIXIA HF R40 onto the same lane. The current version keys on camera_model (with source as the fallback for screen captures and anything else without EXIF Make/Model), which is the right granularity: different physical cameras get different lanes, but two clips from the same camera always share one.

  • OBS pinned to the bottom. Channel allocation is otherwise pure first-seen chronological order, but OBS is pre-seeded into the channel map so it always claims ch1/2 whenever any OBS clip exists. Reason: in a sync pair, the user always wants the screen capture below the camera angle, regardless of when the OBS clip happened to fall in the batch. It's the only camera-source-specific rule in the allocator; other "primary screen-capture" tools could be folded into the same rule if they ever appeared.

  • Force CFR re-encode when the rate doesn't match. Stream-copy is fast, but it preserves the source frame rate verbatim. OBS records at exactly 30.000 fps, the project rate is 29.97 — and dropping the OBS clip into the VSE would cause Blender to auto-flip the scene fps (and back) and the OBS video to play at 0.1% slowdown, drifting out of sync with paired audio over the length of the clip. The fix: any clip whose source fps deviates from the target (with 0.01 tolerance for 30000/1001 jitter) takes the CFR re-encode path. Clean clips at the target rate keep stream-copying.

  • Idempotency as a habit. Skipping existing outputs and pruning the output folder from scans both come from the same instinct: re-running should be cheap and safe, never destructive. The conform-to-WAV pass skips its own _extaudio.wav if it already exists, too.

  • Loudness target of -16 LUFS / -1.5 dBTP. A sensible web/streaming loudness with about 1.5 dB of true-peak headroom, so mixed-source audio sits at a consistent level instead of lurching between a quiet camcorder and a loud phone.

  • A quirk preserved in the macro docs. Keyboard Maestro's Repeat count must be the bare variable name BlenderDeleteCount (no percent signs), because that field is a calculation, not text. The README calls this out because it trips people up every time.

  • Two repos became one, with history. The Keyboard Maestro tool started life as its own 8-commit git repository. It was folded into this repo with git subtree so all eight of its original commits are preserved in the combined history — not flattened away — and it now reads as pipeline "step 4.5".

Part VI - How to Use It: Full Walkthrough

Install the dependencies (macOS): brew install ffmpeg imagemagick exiftool, install Blender, and install Keyboard Maestro for the cutting step. avconvert is already built into macOS. If you plan to use external audio files or camera-sync pairs: pip install audio-offset-finder.

1. Ingest. Scan the footage and read the report:

python3 ingest.py ~/footage/trip

The script scans and reports, then asks two questions in sequence. First:

Any of these clips have a separate external audio file? [y/N]:

If you recorded a Voice Memo or used a separate recorder alongside any clip, answer y and drag-and-drop each video + audio file pair when prompted.

Any clips from two cameras recording the same take, to sync onto separate tracks? [y/N]:

If you captured one take from two cameras simultaneously (typically an OBS screen recording plus a DSLR angle), answer y and drag-and-drop the base clip (whose audio anchors the sync) followed by the second-camera clip. Otherwise press Return to skip either prompt. Open ~/footage/trip/_ingest/ingest_report.md and skim the flags, the Pairings section, and the timeline gaps. If a camera with no phone clip in the batch got the wrong time, re-run with the real offset:

python3 ingest.py ~/footage/trip --local-offset -04:00

2. Transcode. Normalize everything (this is the slow step):

python3 transcode.py ~/footage/trip

Videos are normalized to SDR/CFR/16:9 MP4. After all the videos finish, any paired external audio is conformed to a sibling WAV and its offset measured; any camera-sync pair has its offset measured the same way. Use --dry-run first if you want to see the plan, or --no-loudnorm to skip audio leveling. The script ends by printing the next command — the import-vse.py invocation with the project path threaded in.

3. Import into Blender. Build the project:

python3 import-vse.py ~/footage/trip --name trip_edit

Pick a resolution; the script shows you the per-camera channel routing legend and the clip order before it builds anything. Confirm and let Blender create trip_edit.blend. The output ends with the next command — opening the .blend and validating it.

4. Edit and mark. Open the .blend, do your rough edit, and place F1…/u marker pairs around every range you want to keep. Then validate:

python3 vse-validate-markers.py ~/footage/trip/trip_edit.blend

The next-step block shows you the fully-resolved trigger.sh <N> command (with the loop count filled in) plus the vse-remove-markers.py command that follows.

4.5. Cut. With Blender open and the mouse hovering over the VSE timeline, run the macro with that loop count:

./blender-km-macros/scripts/trigger.sh <loop-count>

(Rehearse with --test <loop-count> first if you like.)

5. Clean up. Remove the now-spent markers:

python3 vse-remove-markers.py ~/footage/trip/trip_edit_cut.blend

That is the whole loop: a folder of mismatched footage in, a clean cut Blender project out.

Troubleshooting quick hits

  • Clips out of order by hours — a camcorder's time was not corrected; re-run ingest with --local-offset.
  • A file sorted to the very end — it had no timestamp metadata; the report flags these. OBS clips with the default YYYY-MM-DD HH-MM-SS.mkv filename are handled automatically; if your OBS template is custom, the filename-based time recovery won't fire.
  • Import found no manifest — you skipped a step; run ingest then transcode first.
  • Macro does nothing — Blender must be running and the mouse must be over the timeline; trigger.sh will warn if Blender is closed.
  • External audio sync looks off in Blender — check the standard_score printed during transcode; a score below 10 means low confidence and the pair is left at offset 0 for manual nudging. The conform-to-WAV step handles the AAC priming and resample drift that used to plague Voice Memo overlays.
  • Two cameras from the same brand sharing a row — the routing key is camera_model, so a clip with no model exposed (some screen-capture tools, generic encoders) falls back to source and may share with another brandmate. Check the channel-routing legend printed at import time.

Part VII - Glossary

  • HDR / SDR -- High / Standard Dynamic Range. HDR clips (iPhone) carry a wider brightness range and must be tone-mapped down to SDR for a normal timeline.
  • PQ / HLG -- the two HDR transfer curves (smpte2084 and arib-std-b67); their presence is how ingest detects HDR.
  • VFR / CFR -- Variable / Constant Frame Rate. Phones shoot VFR; editors want CFR (here, 29.97 fps) so audio and video stay in sync.
  • FPS / 29.97 -- frames per second. 29.97 (technically 30000/1001) is the pipeline's target timeline rate.
  • LUFS / dBTP -- Loudness Units Full Scale / decibels True Peak. The audio targets: -16 LUFS average loudness, -1.5 dBTP peak ceiling.
  • loudnorm -- the ffmpeg filter that measures and adjusts loudness to those targets.
  • Ken Burns -- the slow pan/zoom applied to still photos so they feel alive.
  • VSE -- Blender's Video Sequence Editor, the timeline the project is built in.
  • zscale / tonemap (Hable) -- the ffmpeg color tools used for non-Apple HDR-to-SDR conversion; "Hable" is a filmic highlight-rolloff curve.
  • letterbox -- fitting non-16:9 content onto a 16:9 frame; here a blurred copy of the clip fills the sides instead of black bars.
  • audio-offset-finder -- the Python tool (pip install audio-offset-finder) that compares two audio tracks and returns the time offset between them, used to sync external audio recordings to their matching video clips.
  • external_audio -- a field written into manifest.json by ingest when you pair a video clip with a separate audio file; transcode reads it to know which clips need an audio sibling WAV conformed and an offset measured.
  • external_audio_source -- the recorder classification ingest assigns to a paired audio file (zoom, voice-memo, or a file-extension bucket). Drives which VSE channel the audio strip lands on.
  • sync_group -- a shared id ingest writes on two manifest entries that captured the same take from different cameras (e.g. OBS + DSLR). One member also gets sync_base: true; transcode measures the audio offset between the pair and writes sync_offset_s onto the other.
  • camera_model -- the full device string each clip exposes (Canon EOS 7D, iPhone 16 Pro, HERO12 Black). Read from ffprobe directly for iPhones, from exiftool for everything else. It's the primary routing key for per-camera VSE channel allocation.
  • per-camera channel routing -- import-vse's allocation rule: every unique camera_model (with source as fallback) gets its own VSE channel pair, every unique external_audio_source gets a single channel above the highest camera pair, OBS is pinned to ch1/2. Result: muting one camera or one recorder is a single click.
  • conform -- transcode's step of resampling a paired audio file to a sibling PCM WAV at the video's native sample rate and channel count. Eliminates AAC priming delay and on-the-fly playback resampling that would otherwise drift the synced audio.
  • manifest -- the JSON file describing every clip; the contract between stages.
  • idempotent -- safe to run again: re-running skips work already done.
  • headless / --background -- running Blender with no window, driven entirely by a script.
  • ffprobe / exiftool / identify -- the inspectors: media streams, EXIF tags, and image dimensions respectively.
  • mov_text / soft-embedded subtitles -- the 3GPP timed-text subtitle stream supported inside MP4 containers. Captions travel with the file like a hard-burn but stay toggleable in compatible players (QuickTime, VLC, iPad, Apple TV). The default output of the optional captions/ add-on.
  • SRT / ASS -- subtitle file formats. SRT is plain-text editable (used as the on-disk source of truth and the input to the mov_text mux). ASS is more expressive (font, color, position, per-event styling) and is what the --burn path generates internally to drive ffmpeg's subtitles filter via libass.
  • Whisper -- OpenAI's open-source speech-to-text model. The captions add-on uses whisper.cpp (Homebrew binary whisper-cli, Metal-accelerated on Apple Silicon) — not the heavier Python package openai-whisper. captions.py calls it as a subprocess with -ojf to get per-token JSON output, then groups tokens into phrase-length SRT entries (or one entry per token with --word-by-word).
  • git subtree -- the merge technique that folded the macro repo into this one while keeping its commit history.
  • percent-TriggerValue-percent -- the Keyboard Maestro token holding the value passed to a macro; here, the number of delete loops.

Appendix A - The blender-km-macros README (verbatim)

blender-km-macros

A small Keyboard Maestro macro manager for a Blender clip-deletion workflow. It bundles the exported macros plus a shell helper so the "Delete clips Blender" macro can be triggered from anywhere (terminal, scripts, other apps), running the clip-deletion cycle a number of times you pass in.

This folder is part of the video-intake-pipeline repository — it provides step 4.5 of that pipeline: the clip-cutting macro you run after vse-validate-markers.py and before vse-remove-markers.py. See the top-level README for the full footage → edit workflow.

Layout within the repo

video-intake-pipeline/              ← repo root (ingest.py, transcode.py, …)
└── blender-km-macros/
    ├── README.md
    ├── macros/
    │   ├── Delete clips Blender.kmmacros          # the real macro
    │   └── Delete clips Blender (TEST).kmmacros   # dry-run version (no deletions)
    └── scripts/
        └── trigger.sh                             # CLI wrapper around the osascript trigger

Importing the macros

Double-click each .kmmacros file to import it into Keyboard Maestro (or drag it onto the Keyboard Maestro Editor). Both import into a macro group named Blender group.

Group availability: the exported group is set to be available in all applications (not restricted to Blender). This is required — the macro brings Blender to the front itself, so it must be allowed to run even when Blender isn't the front app. After importing, confirm the Blender group shows "available in all applications."

Using trigger.sh

scripts/trigger.sh triggers a macro and passes a number through as the macro's parameter. That number is how many times the macro repeats the clip-deletion cycle.

./scripts/trigger.sh 5           # run the REAL macro, 5 delete cycles
./scripts/trigger.sh --test 5    # run the TEST macro (no deletions), see below
./scripts/trigger.sh -t 5        # same as --test

Paths above are relative to this blender-km-macros/ folder. From the repo root, prefix with the folder name — e.g. ./blender-km-macros/scripts/trigger.sh 5 — which is the form the top-level README uses for step 4.5.

  • Requires a number argument (after the optional -t/--test flag).
  • Exits with an error and a usage message if the number is missing.
  • If Blender isn't running, it does not trigger the macro — it prints a message to stderr, posts a macOS notification, and exits 1. (The KM gate is still a backstop for other trigger paths.)
  • The script is executable; if needed, restore the bit with chmod +x scripts/trigger.sh.

Manual triggering with osascript

The same triggers without the wrapper script — substitute your count for 5:

osascript -e 'tell application "Keyboard Maestro Engine" to do script "Delete clips Blender" with parameter "5"'
osascript -e 'tell application "Keyboard Maestro Engine" to do script "Delete clips Blender (TEST)" with parameter "5"'

The macros read the passed value via the %TriggerValue% token.

How the macro works

Delete clips Blender is a single, self-contained macro in the Blender group. When triggered with parameter N, it runs this sequence:

  1. Gate — only if Blender is open. If Blender is not running, it shows a message and cancels. Nothing else happens.
  2. Bring Blender to the front. Activates Blender so the simulated keystrokes are guaranteed to land in Blender and not whatever app you triggered from.
  3. READY? prompt. A prompt tells you to move the mouse over the Blender VSE timeline (required — those shortcuts only work when the mouse is over the timeline), then press Return to start or Escape to cancel.
  4. Capture the count. A Set Variable to Text action stores the passed parameter (%TriggerValue%) into the variable BlenderDeleteCount.
  5. Repeat the delete cycle N times. A Repeat action whose count is the calculation BlenderDeleteCount runs the fixed clip-deletion keystroke sequence (with 1-second pauses) N times. The count is driven entirely by the argument passed from trigger.sh / osascript — there is no hard-coded count.

The Repeat count must be the bare variable name BlenderDeleteCount (no % signs) — that field is a calculation, not text. Putting %TriggerValue% or %BlenderDeleteCount% there shows "invalid." The editor may briefly show "invalid" until the variable has a value; that's just a preview and it works at run time (the Set Variable action runs first).

Testing it safely (the TEST macro)

Delete clips Blender (TEST) runs the same front-half flow — gate, bring-to-front, READY? prompt — but replaces the delete keystrokes with a confirmation dialog instead of actually deleting anything. Use it to confirm the flow works end to end (including that the count is passed through correctly) before running the real thing:

./scripts/trigger.sh --test 5

After you press Return (Start) at the READY? prompt, you'll get a "✅ TEST PASSED" dialog that echoes the count it received (5), with an OK button. No clips are touched.

Notes

  • These files are exported from a working Keyboard Maestro setup (with one action — the TEST macro's "✅ TEST PASSED" confirmation — appended afterward), so they should import cleanly. The TEST macro's gate cancels silently if Blender isn't open (its "Blender isn't open" message did not survive an earlier import); add a message there in the editor if you want one.
  • A bare hotkey is intentionally not set: the count comes from the passed parameter, so the macros are triggered by name (via trigger.sh, osascript, or an Execute a Macro action), not a keypress.
  • The Blender group is available in all applications (required so the macro can bring Blender to the front from anywhere).

After any edit in Keyboard Maestro, re-export the macro over the matching file in macros/ to keep the macros in sync — that round-trip is the source of truth, not hand-edited XML. Commit the re-exported .kmmacros in the combined video-intake-pipeline repo; this folder no longer has its own git history — it was merged in via git subtree.
